# Your role

Act as a senior business analyst and software requirements engineer. Create a complete, detailed Software Requirements Specification (SRS) for the project below.

Produce the SRS itself—not a project pitch, implementation plan, or code. Write for product owners, developers, testers, security reviewers, and project sponsors.

Use the structure and good requirements-writing practices of ISO/IEC/IEEE 29148:2018 as guidance. Do not claim the document is formally compliant or certified.

# Project idea

The project is an AI-powered autonomous software testing agent. A user provides a software project, codebase, application package, or authorized running application. The agent inspects the software and its available environment, determines which types of testing apply, creates a test plan, generates or configures test scripts, runs the tests using suitable tools, evaluates results against evidence and defined expectations, and reports failures, coverage gaps, limitations, and improvement suggestions.

The agent should choose tests based on the specific software and available access. It should not blindly run every possible test type. It must distinguish tests that passed, failed, were flaky, skipped, blocked, inconclusive, unsupported, or ended in a testing-platform error. It must not claim that software is defect-free or that an untested area passed.

# How to handle missing information

Do not invent product decisions, limits, integrations, or performance targets.

- Mark unknown values as `TBD`.
- Add every `TBD` to an open-questions register.
- If a temporary assumption is needed to make the SRS readable, label it with a unique assumption ID, explain its impact, and identify who should confirm it.
- Separate confirmed project requirements from proposed defaults and assumptions.
- Clearly separate **MVP**, **Later phase**, and **Optional** capabilities.
- Prioritize requirements as **Must**, **Should**, **Could**, or **Won’t for this release**.
- Do not present future or unsupported capabilities as available product features.

# Writing quality

- Make the SRS complete, specific, consistent, and easy to navigate.
- Give every requirement a unique ID and one main obligation.
- Use testable “The system shall…” statements.
- Give each requirement acceptance criteria and a verification method.
- Avoid vague words such as “fast,” “secure,” “easy,” “intelligent,” and “complete” unless you define measurable criteria.
- Explain requirement dependencies and conflicts.
- Include a glossary and use each term consistently.
- Include requirement IDs in use cases, acceptance criteria, and the traceability matrix.
- If the document is too long for one response, divide it into numbered parts. Preserve the original table of contents and continue without omitting or summarizing required sections.

# Product scope

Define the system as a platform containing:

- Project intake and validation.
- Project inspection and capability detection.
- An AI-assisted test planner.
- Test script generation or configuration.
- A registry of testing capabilities and tool adapters.
- Isolated test execution workers.
- A deterministic result evaluator.
- Evidence and artifact storage.
- Failure analysis and improvement recommendations.
- A dashboard for projects, plans, runs, results, and history.
- Human approval and authorization controls.

The system should be extensible so that testing tools, project types, and specialist testing capabilities can be added. Do not imply that an adapter exists unless the SRS identifies it as a confirmed, implemented capability.

# Required agent workflow

Specify the system behavior and requirements for this full workflow:

1. The user creates a project or run and provides software, target, and scope.
2. The system validates inputs and confirms the authorized target.
3. The agent inspects the project, identifying its type, technology, instructions, existing tests, routes, APIs, schemas, dependencies, and available tools.
4. The agent creates a test plan. Each proposed check identifies its target, category, rationale, risk, prerequisites, expected result, source of that expectation, tool, and resource limit.
5. The agent classifies each check as applicable, not applicable, unsupported, blocked, or awaiting authorization.
6. The user can review or edit the plan. Specify which safe checks may run automatically and which actions require approval.
7. The agent generates or configures scripts and validates them before execution.
8. An execution worker runs checks in a controlled environment and records progress.
9. A deterministic evaluator assigns statuses using assertions, runner output, contracts, thresholds, and evidence.
10. The agent analyzes failures and creates findings and suggestions, clearly separating confirmed facts from hypotheses.
11. The user reviews the report, artifacts, and generated scripts and can stop, retry, or rerun relevant checks.
12. If the user explicitly authorizes changes, the system may update tests or application code and run verification again. Otherwise, it must leave tested application code unchanged and provide suggestions only.

Include a Mermaid or text workflow diagram.

# AI-specific requirements

Define testable requirements for:

- Project classification and confidence reporting.
- Test-plan generation and explanation.
- Test-case, test-data, and script suggestions.
- Failure grouping and root-cause suggestions.
- Improvement recommendations ranked by impact and confidence.
- Structured AI outputs and validation before use.
- Resistance to prompt injection in source files, documentation, web pages, and test data.
- Separation of AI planning from script execution and result evaluation.
- Disclosure of generated, inferred, and human-confirmed findings.
- User configuration of AI provider, model, and credentials.
- Secure storage and redaction of AI-provider credentials.
- Minimizing project data sent to remote AI providers.
- Local or AI-disabled operation where feasible.
- Behavior when an AI provider is unavailable, rate-limited, or returns invalid output.

The AI must not be the sole authority for a Passed result. AI may explain evidence or suggest next steps; deterministic checks and explicit criteria determine test status.

# Result model and reporting

Specify these statuses for individual checks:

- **Passed** — the check ran and all defined assertions passed.
- **Failed** — the check ran and a defined assertion failed.
- **Flaky** — the check failed on one attempt and passed on a retry; preserve both outcomes.
- **Skipped** — the check was not run, with a reason.
- **Blocked** — required setup, access, or user input was unavailable.
- **Inconclusive** — the check ran, but the expected behavior or evidence was insufficient to decide.
- **Unsupported** — the available implementation cannot test the capability or target.
- **Error** — the testing platform failed to complete the check.

Specify that the overall verdict applies only to the tested scope and must not hide skipped, blocked, flaky, inconclusive, or unsupported checks.

Each report must include:

- Project and target details, version, branch, or commit when available.
- Scope, environment, assumptions, and configuration.
- Run start time, end time, duration, and status.
- Planned and executed checks, with reasons for inclusion and omission.
- Results by testing category and individual check.
- Failures with severity, reproduction steps, expected and actual behavior, and evidence.
- Logs, screenshots, traces, responses, measurements, and generated scripts where available.
- Flaky, skipped, blocked, inconclusive, unsupported, and error checks.
- Coverage gaps and limitations.
- Improvement suggestions with evidence and confidence labels.
- Human-readable and machine-readable report formats.

# Safety and authorization requirements

Specify that:

- Testing is restricted to targets the user is authorized to test.
- The test scope is visible and validated before execution.
- Destructive tests, external active security testing, production changes, and high-volume traffic require explicit approval.
- Untrusted projects and generated scripts run with isolation, timeouts, resource limits, and controlled network access where supported.
- Secrets must not appear in logs, prompts, reports, screenshots, or artifacts.
- The system must not change tested application code unless the user explicitly enables and approves fix mode.
- The product must disclose when suitable isolation is unavailable and restrict execution accordingly.
- Users can cancel runs, and the system records the cancellation outcome.

# Requirement format

Use a consistent table format for each requirement:

| Field | Description |
|---|---|
| ID | Unique ID, such as `FR-PLAN-001` |
| Name | Short requirement title |
| Requirement | One “The system shall…” statement |
| Priority | Must / Should / Could / Won’t for this release |
| Phase | MVP / Later phase / Optional |
| Rationale | Why the requirement exists |
| Source | User request, assumption, or stakeholder decision |
| Preconditions | Required conditions |
| Acceptance criteria | Measurable pass conditions |
| Verification method | Test, inspection, analysis, or demonstration |
| Dependencies | Related requirements or external systems |

Use prefixes such as `FR` for functional requirements, `NFR` for non-functional requirements, `AI` for AI-specific requirements, `SEC` for security, `SAF` for safety, `DATA` for data, and `INT` for interfaces.

# Final quality review

Before delivering the SRS, check that:

- Every requirement has a unique ID and can be verified.
- Every product goal maps to one or more requirements.
- Every feature has acceptance criteria.
- Requirements do not conflict or duplicate one another.
- Confirmed requirements are distinct from design assumptions.
- Unsupported and future testing capabilities are not described as guaranteed.
- Every `TBD` appears in the open-questions register.
- AI opinion alone cannot create a Passed result.
- Safety, authorization, privacy, and retention cover source code and generated artifacts.
- MVP requirements are separated from later phases.
- The traceability matrix links requirements to product goals, use cases, and verification methods.

End with a concise list of stakeholder decisions needed before implementation begins. Do not guess when a decision is unresolved.
