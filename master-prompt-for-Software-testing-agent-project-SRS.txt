Task
Create a complete, detailed Software Requirements Specification (SRS) for the project described below.

The output must be an SRS document—not a project pitch, implementation plan, or code. Use the structure and good requirements-writing practices of ISO/IEC/IEEE 29148:2018 as guidance. Do not claim the SRS is formally compliant or certified.

Write the document so that product owners, developers, testers, security reviewers, and project sponsors can understand what the product must do and how its requirements can be verified.

Project idea
The product is an AI-powered autonomous software testing agent. A user provides a software project, codebase, application package, or authorized running application. The agent inspects what it can access, determines which types of testing are applicable, creates a test plan, generates or configures test scripts, executes them using appropriate tools, evaluates results against evidence and defined expectations, and reports defects, limitations, coverage, and improvement suggestions.

The agent should select tests for the software it receives rather than blindly running every possible test type. It should distinguish tests that passed from tests that failed, were skipped, were blocked, were inconclusive, or are unsupported. It should not claim that software is defect-free or that an untested area has passed.

Instructions for writing the SRS
Be complete and specific. Explain product behavior, users, system boundaries, features, data, interfaces, security, safety, AI behavior, and verification criteria.

Separate requirements from design. Specify required behavior without forcing unnecessary implementation choices. Put implementation options in a clearly labeled design considerations or assumptions section.

Do not invent decisions. When a value or product decision is unknown, mark it TBD and add it to an open-questions register. If you need a working assumption, label it with a unique assumption ID, explain its impact, and identify who should confirm it.

Distinguish delivery phases. Label each requirement as:

MVP — required for the first usable release.

Later phase — planned extension.

Optional — configurable or dependent on customer needs.

Prioritize requirements as Must, Should, Could, or Won’t for this release.

Make every requirement testable. Use unique IDs, one principal obligation per requirement, and measurable acceptance criteria. Avoid words such as “fast,” “secure,” “easy,” “intelligent,” or “complete” unless they are defined with a measurable criterion.

Use consistent terminology. Include a glossary and do not use different labels for the same concept.

Make applicability explicit. Not every test type applies to every software project. State how the agent determines applicability and how it explains tests that it cannot run.

Use tables where they improve traceability. Include requirement IDs in feature descriptions, use cases, and acceptance criteria so readers can follow them.

Identify conflicts and dependencies. Explain requirements that depend on user-provided access, source code, test data, external services, platform support, or AI-provider configuration.

Product scope
The SRS must define the product as a platform with:

A user interface for project intake, test planning, run control, findings, artifacts, and history.

A project inspection and capability-detection service.

An AI-assisted planner that selects applicable tests and explains its choices.

A test-script generation or configuration capability.

A registry of testing capabilities and tool adapters.

An isolated test execution service or worker.

A deterministic evaluator that assigns test results from evidence.

Evidence and artifact storage.

A reporting and recommendations service.

An AI-provider interface for planning and explanation, with clear configuration and privacy behavior.

The architecture should be extensible so that new test agents, test tools, and software types can be added. The SRS must not present a capability as implemented or available merely because it appears in the future capability catalog.

Agent workflow to specify
Describe the complete workflow and requirements for each step:

User creates a project or testing run and supplies software and scope.

System validates input and authorization.

Agent inspects the project and discovers its type, stack, instructions, existing tests, routes, APIs, schemas, dependencies, and available tools.

Agent creates a test plan. Each planned check identifies its target, category, purpose, risk, prerequisites, expected result, source of that expectation, tool, and resource limit.

Agent identifies which checks are applicable, not applicable, unsupported, blocked, or awaiting authorization.

User can review or adjust the plan. Define which safe checks may start automatically and which actions require approval.

Agent generates or configures scripts and validates them before execution.

Execution worker runs checks in a controlled environment and records progress.

Evaluator assigns a result using test output, assertions, contracts, configured thresholds, and collected evidence.

Agent analyzes failures and prepares clearly labeled findings and suggestions.

User reviews the report, artifacts, and generated scripts; can cancel, retry, or rerun relevant checks.

If explicitly authorized, system can apply permitted fixes or update tests and run verification again. Otherwise, it provides suggestions without changing tested application code.

Include a text-based or Mermaid workflow diagram.

AI-specific requirements
Specify requirements for:

Project classification and confidence.

Test-plan generation and explanation.

Test-case, test-data, and script suggestions.

Failure grouping and root-cause suggestions.

Improvement recommendations, ranked by impact and confidence.

Structured AI outputs that are validated before use.

Prompt-injection resistance when reading source files, documentation, web pages, or test data.

Separation of AI planning from script execution and result evaluation.

Disclosure of AI-generated or inferred findings.

User configuration of AI provider, model, and credentials.

Secure storage and redaction of AI-provider credentials.

Data-minimization controls for source code and project data sent to remote AI services.

Optional local or AI-disabled operation where feasible.

Behavior when the AI provider is unavailable, rate-limited, or returns invalid output.

The AI must not be the sole authority for declaring a test passed. It may explain evidence and propose next steps; deterministic checks and explicit criteria determine pass/fail.

Result model and reports
Define requirements for individual test statuses:

Passed — the check ran and all defined assertions passed.

Failed — the check ran and a defined assertion failed.

Flaky — the check failed on one attempt and passed on a retry; preserve both results.

Skipped — the check was not run, with a reason.

Blocked — required setup, access, or user input was unavailable.

Inconclusive — the check ran, but expected behavior or evidence was insufficient.

Unsupported — the capability or target could not be tested by the available implementation.

Error — the testing platform failed to complete the check.

Specify that the overall verdict must be limited to the tested scope and must not hide skipped, blocked, flaky, or unsupported checks.

Each report must include:

Project and target details, version, branch, or commit when available.

Scope, environment, assumptions, and configuration.

Run start time, end time, duration, and status.

Planned and executed tests, with reasons for inclusion or omission.

Results by test category and individual check.

Failures with severity, reproducible steps, expected and actual result, and evidence.

Logs, screenshots, traces, responses, measurements, and generated test scripts where available.

Flaky, skipped, blocked, inconclusive, unsupported, and error checks.

Coverage gaps and limitations.

Improvement suggestions with evidence and confidence labels.

A machine-readable report format and a human-readable report format.

Do not invent numeric targets. Propose candidate values only in a clearly labeled “Proposed defaults requiring stakeholder approval” table, with a rationale and a TBD marker until accepted.

Safety and authorization requirements
Specify that:

Testing is restricted to targets the user is authorized to test.

Scope is visible and validated before execution.

Destructive tests, external active security tests, production changes, and high-volume traffic require explicit approval.

Untrusted projects and generated scripts are executed with isolation, timeouts, resource limits, and controlled network access where supported.

The system must not expose secrets in logs, prompts, reports, screenshots, or artifacts.

The system must not modify tested application code unless the user explicitly enables and approves fix mode.

The platform must clearly disclose when suitable isolation is unavailable and restrict execution accordingly.

Users can cancel a run and the system records the cancellation outcome.

Requirement format
Write each requirement in a consistent format, for example:

Field	Description
ID	Unique ID, such as FR-PLAN-001
Name	Short requirement title
Requirement	“The system shall…” statement
Priority	Must / Should / Could / Won’t for this release
Phase	MVP / Later phase / Optional
Rationale	Why this requirement exists
Source	User request, assumption, or stakeholder decision
Preconditions	Required conditions
Acceptance criteria	Measurable pass conditions
Verification method	Test, inspection, analysis, or demonstration
Dependencies	Related requirements or external systems
Use separate ID prefixes, such as FR for functional, NFR for non-functional, AI for AI-specific, SEC for security, SAF for safety, DATA for data, and INT for interfaces.

Quality review before delivery
Before presenting the SRS:

Check that every requirement has a unique ID and is testable.

Check that every project goal maps to one or more requirements.

Check that every feature has acceptance criteria.

Check that requirements do not conflict or duplicate each other.

Check that requirements distinguish product behavior from implementation assumptions.

Check that unsupported or optional testing areas are not represented as guaranteed capabilities.

Check that all TBD items appear in the open-questions register.

Check that the requirements and test statuses do not allow AI opinion alone to create a pass result.

Check that safety, authorization, privacy, and data-retention requirements cover both source code and generated artifacts.

Check that the MVP is clearly separated from later-phase capabilities.

End the SRS with a concise list of stakeholder decisions needed before implementation begins. Do not omit unresolved decisions; identify them clearly instead of guessing.
